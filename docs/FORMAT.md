# 光盘格式笔记

对象：`300nes_disc v1.iso`（Super Game VCD 300 / `NES_DISK V1`，
SunPlus/Rolsen 芯片 DVD 播放器专用非标准 VCD）。

## 1. 镜像层

不是标准 ISO9660：**2352 字节/扇区，Mode 2 Form 1 原始镜像**。

- 扇区同步头：`00 ff ff ff ff ff ff ff ff ff ff 00`
- 用户数据起始偏移：**24**（12 同步 + 4 头 + 8 子头）
- 每扇区有效数据 2048 字节
- PVD 在第 16 扇区（文件偏移 `16*2352+24 = 37656`）

```
iso_offset(sector) = sector * 2352 + 24
```

## 2. 目录结构

| 目录 | 内容 |
|---|---|
| `CDI/` | `CDI_ALL.RTF`(全 0)、`CDI_BUM.DAT`(背景音乐)、`CDI_FONT.FNT`(点阵字库)、`CDI_VCD.APP` |
| `EXT/` | `LOT_X.VCD`、`PSD_X.VCD` |
| `MPEGAV/` | 空 |
| `NEWROM/` | 300 个 `G001.BIN` ~ `G300.BIN`，共 34.5 MB |
| `SEGMENT/` | 31 个 `ITEM0001.DAT` ~ `ITEM0031.DAT`，共 9.5 MB |
| `VCD/` | `ENTRIES.VCD`、`INFO.VCD`、`LOT.VCD`、`PSD.VCD` |

## 3. NEWROM/*.BIN 格式

```
偏移 0x00    MIPS 跳转桩
0x0000  lui   $8, 0x4002
0x0004  addiu $8, $8, <目标低 16 位>
0x0008  jr    $8
0x000C  nop
```

跳转目标落在 **0x4002xxxx**（播放器固件区）。实测只有 3 个取值：

```
0x400269E0   0x40026AF0   0x400269B0
```

> **推论**：模拟器本体在播放器固件里，不在这张盘上。三个地址对应三种
> mapper 处理例程 —— 这就是为什么 `.BIN` 里没有 mapper 字段，
> **mapper 编码在跳转地址里**。

ROM 数据起点：

```
rom_start = be16(bin[6:8]) + 0x61C0
```

实测 G001 的 `be16 = 0x69E0`，`0x69E0 + 0x61C0 = 0xCBA0 = 52,128`。

之后是 PRG + CHR，尾部 4~5 KB 是播放器校验/控制数据。

## 4. SEGMENT/*.DAT 格式（部分破解）

每个 ITEM 恰好 **307,200 字节 = 150 扇区 × 2048**，是 VCD 的一个 Segment。

内部是 MPEG-PS，但**混入了两种 PES 流**：

| 流 ID | 数量 | 用途 |
|---|---|---|
| `0x1E1` | 16 | 视频（MPEG-1） |
| `0x1E2` | 54 | 音频（MP3） |

扇区布局：**每 2048 字节扇区 = 12 字节 pack 头 + 6 字节 PES 头 + 2030 字节负载**，
但有 79 个扇区**没有 pack 头**（属于上一个包的续接）。

```
扇区 N:  00 00 01 BA | 8 字节 | 00 00 01 E1 | 09 02 | 负载 2030 字节
```

注意 `09 02` = 2306，**大于扇区容量**，说明这个长度字段不可信（所有 E1 包都是
同一个值 0x0902），实际每包只装 2030 字节。

### 序列头

视频流第一个字节之后就是标准序列头：

```
00 00 01 B3  16 01 20 83 ...
             └─ 352 × 288（PAL VCD half-D1）
```

### 当前解码结果

按「只取 0x1E1 负载」重组裸流（32,480 字节），`ffmpeg -f mpegvideo` 能解出
**一帧 352×288**，画面是经典的黄色菜单底色 + 底部残缺的文字，但大量
`ac-tex damaged` / `skipped MB`。

按「含无包头扇区、跳过 E2」重组（194 KB）反而更差。

**未解决**：为什么 I-frame 数据不完整。怀疑还有一批视频数据藏在
无 pack 头的扇区里，被 E2 包切断；或者长度字段的真实含义不是 PES 长度。

### 试过但失败的方案

| 尝试 | 结果 |
|---|---|
| 把 `0x1E1` 改成 `0x1E0` 交给 ffmpeg | `unknown codec` |
| 每包剥 8 / 12 / 16 字节头 | 全是同一张全灰图 |
| 按 PES 长度 2306 连续切分 | 越切越乱（包实际按 2048 对齐） |
| 整段 306 KB 直接解 | 解出 704×576 但内容错乱 |

## 5. 300 → 146

用库内 8,366 个可解析 ROM 建索引，按 PRG 开头做多偏移哈希
（0/32/64/128/256/512/1024 字节），300 个全部匹配成功。

换皮示例：

```
004, 019, 203, 219  →  Battle City - Super Tank II (Unl)
001, 236            →  1942
002, 285            →  1944
```

## 7. 2026-10-31 第二次攻坚：发现双重视频流

上一节的「私有流 0x1E1」判断**不完整**。用扇区类型序列把整个 ITEM 摊开看：

```
扇区类型序列（V=0x1E1包 A=0x1E2包 P=包头无PES .=无包头续接）
    0: PVVVVVVVVVVVVVVVAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
   50: AAAAAAAAAAAAAAAAAAAAV.............................
  100: ..................................................
统计: {'.': 79, 'A': 54, 'V': 16, 'P': 1}
```

**关键发现**：`0x1E2` 不是音频，**里面全是切片起始码**。

```
E1 包的切片号: 1, 3, 5, 7, 9, 11, 13, 15, 17      （只有奇数）
E2 包的切片号: 1, 2, 3, 4, 5, 6, 7, 8, ...          （连续）
```

分别解码：

| 流 | 裸流大小 | 分辨率 | 切片数 |
|---|---:|---|---:|
| `0x1E1` | 32,468 | 352×288 | 9（奇数） |
| `0x1E2` | 109,608 | **704×576** | 32 |

结论：**这是一个 ITEM 里装了两张独立图像**，不是一条流的拆分。0x1E1 那份只有
奇数切片，更像是「局部更新层」；0x1E2 是 704×576 的主画面层。

拼接两条流会互相污染，必须分开解。

### 仍未解决

- `0x1E1` 只有 9/18 切片，缺失的偶数切片找不到落点
- `0x1E2` 32/36 切片，缺 18 号等少数几片
- 每个分片包载荷开头都有 `ff 0f` 两字节，试过剥 0/2/4 字节，切片序列不变
